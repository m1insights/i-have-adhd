> my node app returns 401s for users who logged in before yesterdays deploy. new logins work fine. whats happening and how do i fix it?
Classic deploy symptom: the deploy invalidated the credential material that old sessions depend on, so anything issued before the deploy no longer verifies, while anything issued after was created with the new material. There are two usual culprits, depending on how your auth works: **1. JWT/token auth: the signing secret changed.** If you verify tokens with something like `jwt.verify(token, process.env.JWT_SECRET)`, old tokens were signed with the old secret and now fail with `invalid signature` → your middleware returns 401. Common ways this happens: - The secret is generated at boot, e.g. `const SECRET = process.env.JWT_SECRET || crypto.randomBytes(32).toString('hex')`. If the env var was never set in prod (or dotenv isn't loaded there), every restart mints a new secret and kills all existing tokens. This is the single most common cause of exactly your symptom. - Someone rotated `JWT_SECRET` in the deploy's env config, or the deploy moved to a new environment/host with a different value. - You switched signing keys/algorithms without accepting the old key during a grace period. **2. Session-cookie auth: the session store was wiped.** If you use `express-session` with the default `MemoryStore` (or sessions in a local SQLite/Redis that got recreated), the deploy's process restart erased all sessions. Old cookies reference session IDs that no longer exist → 401. New logins create fresh sessions, so they work. **How to tell which:** look at the actual error your auth middleware logs for a failing request. `JsonWebTokenError: invalid signature` means case 1; a cookie that comes in but matches no session means case 2. You can also take a failing user's token, decode it (jwt.io or `jwt.decode`), and try verifying it against your current secret. **Fixes:** - Case 1: set `JWT_SECRET` as a stable, explicit env var in your deploy config and remove any random-fallback logic — make the app crash at startup if it's missing rather than silently generating one. If the rotation was intentional, either verify against both old and new secrets for a transition window (try new, fall back to old) or accept that everyone re-logs-in once. - Case 2: move sessions to a persistent external store (`connect-redis`, `connect-pg-simple`, etc.) so restarts and deploys don't drop them.
